# AILF Enterprise Readiness Assessment and Roadmap

Updated: 2026-02-21
Scope: 当前 AILF 仓库（前端 React+TS+AMIS、后端 FastAPI、MySQL、Redis、Celery、推理工作流）

## 1. Executive Summary

结论：当前架构可以支持中小规模生产，但还不属于“可审计、可扩展、可高可用”的完整企业级架构。

建议评分（10 分制）：
- 架构可扩展性：7.0
- 交付效率：8.0
- 可靠性（HA/容灾）：5.5
- 安全与合规：5.0
- 可观测性与运维：6.0
- 综合：6.5

一句话判断：
- 适合“快速上线+持续迭代”
- 暂不适合“强 SLA / 强监管 / 大规模多租户”的企业核心系统

## 2. Current Strengths

- 技术栈主流且工程落地成本可控：FastAPI + Celery + Redis + MySQL + React。
- 业务模型灵活：动态路由、工作流引擎、AMIS 动态界面，扩展速度快。
- 推理链路已异步化：AI 任务不阻塞主请求，具备后续横向扩展基础。
- 配置化驱动明显：开发者配置能力完整，适合快速迭代复杂流程。
- 已有监控意识：运行监控页、推理节点状态与 Redis 状态已开始建设。

## 3. Gaps to Enterprise Grade

### 3.1 Reliability and High Availability

- 关键组件可能单点：Redis/MySQL/Broker/Worker 的故障切换策略不完整。
- 缺少标准化容量模型：峰值并发、队列堆积阈值、回压策略未体系化。
- 长链路失败恢复策略不足：工作流步骤重试、幂等、补偿机制有待强化。

### 3.2 Security and Compliance

- 密钥与敏感配置治理不足：需要统一 secret 管理、轮换、最小权限。
- Token 生命周期治理需增强：吊销机制、会话并发控制、审计留痕需完善。
- API 安全防护体系不完整：限流、WAF/网关策略、异常访问告警需要补齐。

### 3.3 Observability and SRE

- 指标体系不完整：缺少统一的 p95/p99、错误率、队列深度、任务成功率看板。
- 缺少链路追踪：请求 ID 与跨服务 tracing 尚未系统化落地。
- 告警闭环薄弱：目前监控展示大于告警治理，自动化处置未成体系。

### 3.4 Engineering Governance

- 配置变更治理可再升级：需要版本化、审批流、回滚点与变更审计。
- 自动化质量门禁不足：契约测试、回归测试、性能基准、故障演练需固化。
- 发布治理不充分：灰度发布、金丝雀、自动回滚策略未完善。

## 4. Target Enterprise Capabilities

目标不是“改成大而全”，而是建立可持续演进的工程底盘：

- 可用性：核心链路达到目标 SLA（例如 99.9% 以上，可按业务目标调整）。
- 安全性：密钥治理、权限最小化、关键操作审计可追溯。
- 可观测性：分钟级定位故障，小时级恢复，日级可复盘。
- 交付性：每周稳定发布，支持灰度和一键回滚。
- 扩展性：新增业务流程主要走配置与模板，而非深度改代码。

## 5. Phased Roadmap (P0/P1/P2)

## P0 (1-2 weeks): Must-have Baseline

- 安全基线
  - 清理默认密钥与弱口令，统一从环境变量/密钥系统注入。
  - 细化开发者 token 与普通用户 token 策略（过期、刷新、吊销、并发会话）。
  - 敏感操作审计日志（登录、权限变更、配置发布）。
- 可靠性基线
  - 明确关键接口超时、重试、幂等策略（尤其工作流节点执行）。
  - Celery 队列与 worker 资源隔离（推理队列、业务异步队列分离）。
  - Redis 连接池、超时、降级策略标准化。
- 可观测性基线
  - 建立统一请求 ID，贯穿前端请求、后端日志、Celery 任务。
  - 关键 SLI 指标可视化：接口错误率、接口 p95、队列堆积、任务失败率。
  - 告警最小闭环：至少覆盖“服务不可用/错误率突增/队列积压”。

P0 验收标准：
- 出现服务抖动时，5-10 分钟内可定位到组件层（API/Redis/Celery/DB）。
- 关键密钥不再硬编码，且可轮换。
- 关键失败场景有明确 fallback 或失败提示，不出现长时间无响应。

## P1 (3-6 weeks): Scale and Governance

- 高可用与容灾
  - Redis 哨兵或集群方案落地。
  - MySQL 主从或等价高可用方案落地。
  - Worker 横向扩缩容策略（按队列长度/耗时阈值）。
- 发布与配置治理
  - 配置版本化、差异对比、可回滚。
  - 灰度发布策略（按用户比例/租户分组/场景分组）。
  - 失败自动回滚流程。
- 质量体系
  - E2E 回归（核心业务流：购票/改签/退票/通知）。
  - 契约测试（动态 API 路由与工作流节点输入输出）。
  - 基础压测与容量基线（峰值吞吐、平均/尾延迟）。

P1 验收标准：
- 任一单点组件故障不导致全系统不可用。
- 配置发布后可在分钟级完成回滚。
- 每次发布前有自动化回归信号，不依赖人工全量冒烟。

## P2 (6-12 weeks): Enterprise Optimization

- 成本与性能
  - 推理机调度策略优化（负载感知、任务分级、冷热队列）。
  - 推理结果缓存和复用策略（带失效规则）。
  - 重型查询拆分、异步化、分页化，减少监控接口长尾。
- 合规与平台化
  - 数据分级与脱敏策略。
  - 合规审计导出能力（按用户/角色/配置变更追溯）。
  - 多租户隔离方案（数据隔离、权限隔离、配额隔离）。

P2 验收标准：
- 资源成本可量化优化（例如单位请求成本下降）。
- 合规审计可按时间、操作者、配置对象快速追踪。
- 支持多业务域并行扩展且不互相影响。

## 6. Suggested KPI / SLO Set

建议先定义一套简单但可执行的指标：

- API 可用性：>= 99.9%
- 关键接口 p95：< 300ms（不含 AI 推理）
- 推理任务成功率：>= 99%
- 推理任务 p95：按模型能力设定分级目标（例如 < 8s）
- 队列积压恢复时间：< 10min
- 配置变更回滚时间：< 5min

## 7. Risks if Not Upgraded

- 随业务量增长，尾延迟和失败率将先于功能问题暴露。
- 配置动态化越强，越需要变更审计和回滚护栏，否则线上风险放大。
- 认证与密钥治理不完善会成为企业采购和上线评审的阻塞项。

## 8. Recommended Next Action

第一步先做 P0，并在项目中建立一个“企业化基线看板”：

- 只追 5 个指标：错误率、p95、队列长度、任务失败率、可用性
- 每周固定复盘一次
- 每次变更必须带回归结果与回滚方案
